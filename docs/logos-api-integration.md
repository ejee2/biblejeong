# Logos API 본문 연결

## 현재 동작

선택한 책을 한 화면에서 스크롤하며 읽는 기존 구조에 Logos API 장 조회를 연결했습니다. API 제공처의 66권 목록과 창세기 1·2·3장, 요한일서 5장의 실제 응답을 로컬 브라우저에서 확인했습니다. 이 확인은 해당 장의 연결 검증이며, 모든 장의 본문과 설명을 검수했다는 의미는 아닙니다.

현재 `assets/api-config.js`는 다음과 같이 API를 비활성화한 상태입니다.

```js
export const BIBLE_API_BASE_URL = '';
```

운영 중계 URL을 확보하기 전에는 기존 데살로니가전서 5:16–20 발췌와 공식 본문 링크가 동작합니다. 설정 파일에는 공개 중계 URL만 넣으며, API 인증키는 넣지 않습니다.

## 구성

```text
GitHub Pages 브라우저
  → 읽기 전용 중계 서버: server/logos-proxy.js
  → Logos API의 문서화된 장 조회
```

| 파일 | 역할 |
| --- | --- |
| `assets/api-config.js` | 공개 중계 서버 주소 |
| `assets/bible-api.js` | 장 요청 대기열, 중복 억제, 상태와 오류 처리 |
| `assets/bible-data.js` | 응답 검증 후 장 등록, 합절 주소 조회 |
| `assets/book-reader.js` | 장별 본문·로딩·재시도 상태 표시 |
| `assets/app.js` | 화면 근처 장 요청, 읽기 위치 유지, 저장 구절 본문 갱신 |
| `server/logos-proxy.js` | 서버 인증, 고정된 제공처 요청, 응답 정제 |

개인 묵상과 구절 표시는 기존 브라우저 저장소를 그대로 사용합니다. 중계 서버에는 책·장 조회만 전송하며, 묵상 내용이나 저장 구절 목록은 전송하지 않습니다. 마이페이지에서는 저장 구절이 속한 장을 요청하고 본문과 상태 영역만 갱신하므로 작성 중인 묵상 편집기는 교체하지 않습니다.

## 중계 서버 계약

`server/logos-proxy.js`는 외부 패키지가 없는 표준 Worker 모듈이며, 기본 export의 `fetch(request, env)`를 지원하는 런타임에 배포할 수 있습니다.

| 서버 설정 | 저장 방식 | 용도 |
| --- | --- | --- |
| `LOGOS_API_KEY` | 서버 런타임의 비밀값 | 제공처 인증 |
| `ALLOWED_ORIGIN` | 서버 환경 설정 | 허용할 브라우저 Origin 하나. 기본값 `https://ejee2.github.io` |

`ALLOWED_ORIGIN`에는 경로나 마지막 `/`를 붙이지 않습니다. 로컬 검증 환경에서는 실제 접속 주소에 맞춰 `http://localhost:4173` 또는 `http://127.0.0.1:4173`으로 설정합니다. 쉼표로 여러 Origin을 나열하는 형식은 지원하지 않습니다.

공개 경로는 다음과 같습니다.

| 요청 | 응답 |
| --- | --- |
| `GET /health` | `{ "ok": true }`. 프로세스 응답만 확인하며 인증키·제공처 연결 상태를 보증하지 않음 |
| `GET /v1/books/{book}/chapters/{chapter}` | 검증된 장 데이터 |
| `OPTIONS /v1/books/{book}/chapters/{chapter}` | 허용된 Origin의 GET 사전 요청 |

장 응답 형식은 다음과 같습니다. 아래 문장은 형식 설명용 예시입니다.

```json
{
  "book": "gen",
  "chapter": 1,
  "verses": [
    { "verse": 1, "endVerse": 1, "text": "첫 절의 본문" },
    { "verse": 2, "endVerse": 3, "text": "합절 본문" }
  ],
  "source": "logos"
}
```

책 ID와 장 경계를 검증하며 제공처 호스트는 코드에 고정되어 있습니다. 임의 URL, 쿼리 매개변수, 본문 쓰기 요청을 전달하는 범용 프록시는 아닙니다. 허용되지 않은 Origin의 장 요청은 거절합니다. Origin 검사는 브라우저 접근 범위 제한이며 사용자 로그인이나 개인별 인증을 대신하지 않습니다.

응답에는 인증 헤더와 원본 오류를 넣지 않습니다. 호출 제한은 `429`와 최대 60초의 `Retry-After`, 제공처 오류는 `502`, 시간 초과는 `504`, 서버 비밀값이 없으면 `503`으로 정제합니다.

## 요청과 데이터 보존

- 클라이언트는 화면 가까이에 있는 장부터 요청하며, 요청 시작 사이에 최소 1100ms를 둡니다. 같은 장은 중복 요청하지 않고, 이미 받은 장을 다시 가져오지 않습니다.
- 책을 바꾸면 대기 중인 요청을 취소합니다. 이미 진행 중인 응답은 등록할 수 있지만 이전 책의 화면으로 되돌리지는 않습니다.
- 요청과 응답 읽기의 제한 시간은 15초입니다. 오류나 `429`는 자동 재시도 루프 없이 버튼으로 다시 시도합니다.
- 장의 식별 정보와 절 범위를 검증한 뒤 전체 응답을 한 번에 등록합니다. 실패한 응답이 기존 발췌나 수신한 장을 덮어쓰지 않습니다.
- 합절은 시작·끝 번호와 본문을 한 행에 유지합니다. 합절 안에 저장한 절은 원래 절 번호를 보존하며, 화면에서는 해당 범위 행을 찾습니다.
- 중계 서버는 성공한 장을 메모리에 5분간 최대 64개 보관하고, 같은 장의 진행 중인 요청을 합칩니다. 캐시와 분당 최대 60개 새 제공처 요청 제한은 런타임 isolate 단위입니다. 여러 isolate 사이에 공유되는 전역 제한은 아닙니다.
- 본문은 실행 중인 메모리에서 사용하며, 전체 성경을 수집해 GitHub 파일이나 배포 번들로 저장하지 않습니다.

## 서버 배포와 활성화

1. 표준 Worker 모듈을 지원하는 서버 런타임을 준비하고 `server/logos-proxy.js`를 진입점으로 지정합니다. GitHub Pages는 이 서버 모듈을 실행하지 않습니다.
2. 해당 런타임의 비밀값 설정에 `LOGOS_API_KEY`를 등록합니다. 키를 소스, URL, 로그, 화면 캡처, 클라이언트 번들에 기록하지 않습니다. `ALLOWED_ORIGIN`은 사용할 웹사이트 Origin으로 설정합니다.
3. 제한된 검증 환경에서 `/health` 응답과 허용된 Origin의 실제 장 조회를 각각 확인합니다. 다른 Origin, 잘못된 책·장, 쓰기 요청과 호출 제한도 확인합니다.
4. 공개 중계 서버가 필요한 경우 공개 URL과 접근 범위를 확인하고 사용자 승인을 받은 뒤 배포합니다. 소유자 전용 주소가 공개 GitHub Pages의 API로 동작한다고 가정하지 않습니다.
5. 서버가 동작하는 URL을 `assets/api-config.js`의 `BIBLE_API_BASE_URL`에 설정합니다. 인증키가 포함되지 않은 HTTPS 중계 주소만 사용합니다.
6. `npm test`와 `npm run build`를 실행합니다. 실제 브라우저에서 여러 장 스크롤, 장절 링크, 모바일 배경창 복귀, 구절 표시, 묵상 작성 중 본문 수신을 확인합니다.
7. 검증한 변경을 `main`에 반영하고 GitHub Actions의 Pages 배포 결과와 실제 사이트를 확인합니다.

연결을 중단하려면 `BIBLE_API_BASE_URL`을 빈 값으로 되돌려 테스트·빌드 후 배포합니다. 브라우저의 기존 표시와 묵상 데이터는 삭제하지 않습니다.

## 이용 범위와 출처

[Logos API 문서](https://www.logos-api.com/docs)의 개인·비상업 이용 범위에서 문서화된 읽기 API를 사용하도록 구현했습니다. 서비스의 API 이용 조건은 성경 번역문의 원저작권과 구별됩니다. 상업화, 원문 파일 배포, 다른 서비스로의 제공 등 범위를 바꿀 때는 제공처 조건과 필요한 원저작권 허락을 각각 확인합니다.

본문의 공급 출처는 Logos API로 표시하고, 성경에 근거한 설명과 사용자의 개인 묵상을 분리합니다. 본문이 연결된 모든 구절에 배경 설명까지 등록된 것은 아니며, 미등록 설명은 그 상태를 표시합니다.

## 진행 상태 — 2026-10-17

- 데이터·로더·읽기 화면·마이페이지·중계 서버 코드가 구현되어 있습니다. 실제 장 응답의 로컬 브라우저 검증도 진행했습니다.
- 운영 중계 서버는 아직 배포되지 않았습니다. Sites에는 소유자 전용 공간 생성과 서버 비밀값 등록까지만 완료했으며, 소스 업로드 단계가 `write_stdin` 승인 정책으로 차단되어 실행 중인 배포가 없습니다.
- 따라서 공개 클라이언트의 중계 URL은 계속 빈 값입니다. 서버 배포가 완료되고 접근 범위를 확인한 뒤 설정 변경·검증·`main` 반영 순서로 활성화해야 합니다.
